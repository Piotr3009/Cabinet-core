# T76 F2 PROBE: WHAT GPT BUILT, ON MAIN AFTER F1

What was probed: everything GPT's decorative-fronts patch put on main at HEAD `26ba367` (T76 F1: `patches/gpt-decorative-fronts.patch` applied with `git apply --3way` on `b810560`, the six conflicts resolved both sides). Every style id and its recipe keys and numbers; every place a recipe is WRITTEN (project, front-material slot, saved door style, unit) and READ (design cascade, engine input, engine pass, hand edits, BOM, materials, Check, CNC, 3D, drawings); the opt-in rule and its activation button; the CNC handoff (back DXF, FRONT DXF per part, `front-operations.json`, the gate); where the AM strips become cut parts; the production state the BOM carries today (the baseline F5 folds); GPT's tests, golden and scripts; the retail surface. This table is the baseline F3 (SS goes), F4 (recipes into the profile, the owner's numbers), F5 (one state), F6 (retail) and F7 (the walk) are measured against.

How: HEAD was checked out into a scratch worktree (`git worktree add --detach <scratch>/head 26ba367`) and the base into a second one (`<scratch>/base b810560`), each with `node_modules` linked, so the integrator's work in progress in the main working tree could not leak into the answers; every line number below is HEAD's. Behaviour was MEASURED with node scripts (kept in the scratch folder, not committed) that import the real modules: `computeCabinet` with `defaultParamsFor(type, DEFAULT_CABINET_PROFILE)`; `migrateDesign`, `resolveUnitDesign`, `frontStyleSelection`; `defaultFrontDecoration`, `normaliseFrontDecoration`, `buildFrontDecoration` on synthetic leaves; the store's `paramsForEngine` and the store itself (`loadProject`, `addUnit`, `addDoors`, `updateUnitParams`, `setDesign`, `setFrontType`, `unitResult`, a JSON save and `loadProject` again); the retail adapter (`setFrontStyle`, `setFrontDecoration`); `buildUnitDxfFiles`; `exportUnitDxfZip`, `exportSheetDxf`, `exportMaterialDxf` with the download captured (GPT's own `captureDownload` pattern) and the ZIP opened with JSZip; `exportGate`; `buildBom`, `resolvePanelMaterial`, `unassignedInUse`, `buildCabinetPartQtys`; `readinessOf`; `buildFrontElevation`, `partDetailDrawing`, `wallDrawingSheets` (the T71 set, Herbal Hill fixture); `frontDecorationGeometry` (three.js in node); both copies of `FrontDecorationControls.jsx` rendered to static HTML (esbuild transform, `react-dom/server`); GPT's eight test files with `node --test`; GPT's classifier; `scripts/t63-copy.mjs` run inside the scratch HEAD worktree. Back DXFs were compared byte for byte against the base worktree. Not measured: anything that needs a browser (the React routing in `UnitView.jsx`, the clicks in `CncView.jsx` and `CncTree.jsx`, GPT's two browser walks); those rows say "read". The full suite was not re-run for this probe (F1's commit records 6292 of 6292). All recipe numbers below are GPT's code defaults on this commit; the leaf in every BUD measurement is the default BUD's one door, 597 x 767 x 25, and every x is the CNC back-view x.

## INTEGRATOR NOTES

- **Retail shows numeric recipe fields today** (F6, lazy client law): `Options.jsx:844-848` mounts the copied controls, measured 2 to 7 typed fields per decorative style, and GPT's retail walk asserts that they are there (`front-decoration-walk.mjs`, "shows editable decoration fields").
- **A blocked recipe holds the whole slab**, not just its pattern: the gate condemns the panel id, so the leaf's back DXF with its hinge cups leaves the ZIP too (measured). F5 wants the slab `cut` and the refusal in the Check.
- **Readiness is `cut` everywhere and READINESS.txt is absent** from every decorated ZIP measured (all lines cut). The AM host carries no `manual` gluing note yet; F7's "ZIP holds ... READINESS.txt" can only hold once something is not `cut`.
- **The BOM identity carries `status`** (`frontDecorationBom.js:15-18`). Measured: two BUD leaves with the SAME G recipe and outline, one blocked by a hand-added back bore (`FRONT_DECORATION_BACK_BORE`), are two FRONT lines, both `readiness: 'cut'`, and their identities differ ONLY by `status`. With `status` deleted (F5) and the slab `cut`, they would merge into one line unless the key keeps the blocked state some other way.
- **AM in the cut list is 2 lines of qty 2**, not 4 lines: top and bottom (and left and right) share outline and mitres. Four parts, four unit rows, four CSV lines and four DXFs do exist.
- **The arch is a ratio, not a semicircle**: rise = `archRatio` x the SHORTER inner side; wide low leaves get a half-ellipse and are never refused; a 300 mm wide A leaf is NOT refused (a semicircle fits). F4 must change the rule, not just a number.
- **No V cutter exists**: `operationProblems` accepts only endmill and ballnose and pairs pocket with endmill; the groove is a capsule pocket with an endmill of min(6, width); the layer name encodes POCKET or FLUTE, not the cutter. And `normaliseFrontDecoration` drops every key that is not in the recipe defaults, so `kind`, `boardMm` or any new key survives only once it is in the defaults F4 moves to the profile.
- **"Margin" differs**: GPT's `grooveInsetMm` insets a region and the comb is centred in it (G's first groove edge at 58 with margin 50). The owner's "margin 60 to the first groove" with pitch 80 needs one stated rule.

- **Saved recipes are explicit**: selecting a style writes the full default object, so any project saved before F4 keeps GPT's numbers after the defaults move.
- **Every `role: 'front'` panel is decorated**, drawer fronts and appliance doors included (BUDR, chests, OVEN_BASE, FRIDGE_US ...). Neither the doc nor the owner's table says so.
- **The unit select freezes a copy**: re-picking the inherited style in RightPanel copies the inherited recipe into `unit.params`, so later project edits do not reach that unit.
